# 枢纽卡：任务说明

你为 ZET 卡片盒写枢纽卡的计划。枢纽卡是进入一个主题的入口：它把承载这个主题的卡分成几组，每张卡占一行，每行说明这张卡贡献了什么。枢纽卡自己不提出新主张。

你只写 JSON 文件。你不写卡片，不改任何卡片。脚本读你的 JSON，建卡、改卡，再用 ZT 检查。

本说明之后附上你的任务文件。任务文件有两种：

- **主题任务**（`t` 开头）：给出几个主题。每个主题写一个 JSON 文件，含一张主题枢纽和若干张线索枢纽。
- **领域任务**（`f` 开头）：给出全部主题的清单。写一个 JSON 文件，含领域枢纽和索引的关键词。

## 枢纽的四个层级

| 层级 | 管什么 | 列什么 |
| --- | --- | --- |
| line（线索） | 一棵树里的一条思路：从一张分支卡起的那一支 | 这一支里的关键卡，以及别的树里接着讲这条思路的卡 |
| topic（主题） | 一棵主题树 | 本树的线索枢纽、核心卡、全部模型卡，以及“邻近”组里别的树的卡 |
| field（领域） | 讲同一大题目的几个主题 | 各主题（脚本把主题换成它的主题枢纽） |
| register（索引） | 整个代理工作区 | 关键词，每个指向一到三个入口 |

## 规则

1. **入口，不是目录。** 不要把一棵树的卡按地址顺序抄一遍：读者在树图里已经看得到这个顺序。只选读者应当从那里进入的卡：每条思路的起点、关键结论、模型卡、反例。一棵大树也只列 10 到 25 行。
2. **按主题分组，不按地址分组。** 每组一个小标题，回答一个问题或代表主题的一个阶段，例如“逆向选择的后果”“应对：信号与甄别”。`groups` 的组数不超过任务文件 `LIMITS` 里的 `max_groups`，`groups` 的总行数不超过 `max_lines`。`neighbours`（脚本写成“邻近”组）不计入这两个上限。
3. **每行一个理由。** 理由是一句话，说这张卡贡献了什么，不少于 `min_reason` 个字。不要重复卡的标题。
4. **走出本树。** 任务文件列出“邻近主题”时，主题枢纽必须有 `neighbours`：一到五行，指向别的树里讲同一问题的卡，每行带关系词：`依赖`、`例示`、`对照`、`放宽`、`对应`、`反驳`，没有合适的就留空。不知道对方哪张卡最合适时，用 `HELPER` 的 `get_tree` 或 `search_cards` 查（只读，命令末尾加 `-Allow` 和任务文件给出的 `ALLOW` 文件，它禁止写入）。
5. **线索枢纽。** 任务文件列出“必须写线索枢纽的分支”时，为每个分支写一张线索枢纽，`anchor` 是那张分支卡。分支不在列表里，不要写。主题枢纽用 `line:<anchor>` 列出每张线索枢纽。一个分支在另一个分支里面时（它的地址以外层分支的地址加 `|` 开头），外层的线索枢纽用 `line:<内层 anchor>` 列出内层的线索枢纽，主题枢纽只列外层的。内层的线索枢纽不能列外层的。
6. **模型卡都要列出**（类型“模型卡”的卡），在主题枢纽或线索枢纽里。模型部件不必列。
7. **标题**是主题的主要主张，一句话，含检索这个主题时会用的词。**范围**一句话，说这张枢纽管哪些卡。标题不能和主题根卡 `<n>/0` 的标题相同，不能和主题枢纽所挂的 `<n>/1` 标题相同，也不能和线索枢纽的 `anchor` 卡标题相同；只差空格或大小写也算相同：写出枢纽的作用，例如“消费需求的分解入口”。预检按 `anchor-title` 拒绝这种标题。
8. **只抄地址顺序的枢纽不要写。** 如果一张主题枢纽的唯一用处是按地址顺序列出本树的卡，读者在树图里已经看得到，不要写它。改为在 `topic` 里写 `entries`：一到三项，每项 `ref` 和一句 `reason`，都是本树的实质卡（不是枢纽卡，也不是 `<n>/0`）。脚本把它们写进主题卡的“## 入口”一节，这棵树就不再要求主题枢纽。预检按 `mirror` 拒绝只抄地址顺序的稿子。这棵树有必须写的线索枢纽时不能走这条：线索枢纽要由主题枢纽列出。
9. **只讲一本书的枢纽会被报告。** ZT 会按已接受的索引词条比较来源：同一个概念在别的书里也有讲法、而 `neighbours` 没列出时，报告 `one-book`，并给出那张卡的地址和它所属的书。真有别的书的讲法时，在 `neighbours` 里写出那张卡和关系；同一关键词不构成关系，写不出关系的就不要写。
10. 文字遵守卡片语言：一句一个陈述，短句，不用分号，主动语态，不用对冲词和夸赞词。

## 主题任务的输出

每个主题写一个文件，路径是任务文件里该主题的“输出文件”。格式：

```json
{
  "tree": "130",
  "topic": {
    "title": "信息不对称让市场萎缩，信号与甄别是两种应对",
    "scope": "主题 130 信息不对称市场的入口。",
    "groups": [
      { "name": "逆向选择的后果", "items": [
        { "ref": "130/2", "reason": "知情者按私人信息决定是否交易，市场因此萎缩。" },
        { "ref": "line:130/2|f", "reason": "逆向选择市场可以有多重竞争均衡，这一支有十二张卡。" }
      ] },
      { "name": "评价标准", "items": [
        { "ref": "130/3", "reason": "约束帕累托最优要求权威同样看不到私人信息。" }
      ] }
    ],
    "neighbours": [
      { "kind": "对照", "ref": "122/1", "reason": "信号传递是知情一方的应对，本主题只讲市场后果。" }
    ]
  },
  "lines": [
    { "anchor": "130/2|f", "title": "逆向选择市场可以有多重竞争均衡",
      "scope": "从 [[130/2|f]] 起的一支。",
      "groups": [ { "name": "…", "items": [ { "ref": "130/2|f|a", "reason": "…" } ] } ],
      "neighbours": [] }
  ]
}
```

`ref` 写卡片地址，不加 `[[ ]]`。线索枢纽写 `line:<分支卡地址>`。没有线索枢纽时 `lines` 写 `[]`。

只抄地址顺序的树不写主题枢纽，改写在主题卡上：

```json
{
  "tree": "130",
  "topic": { "entries": [
    { "ref": "130/2", "reason": "消费需求分成数量与结构两部分。" },
    { "ref": "130/5", "reason": "结构变化改变总量。" }
  ] },
  "lines": []
}
```

`entries` 和 `groups` 只能选一种；有 `lines` 时必须写主题枢纽的 `groups`。

## 领域任务的输出

读任务文件给出的主题清单（一条命令）。把讲同一大题目的主题归成领域：每个领域 `field_min` 到 `field_max` 个主题。一个主题可以属于两个领域。归不进任何领域的主题不要硬归，脚本把它们放进索引的“未归入领域的主题”。再选 30 到 80 个关键词：读者会用来找主题的词，每个指向一到三个入口。

写到任务文件的 `OUT` 路径：

```json
{
  "fields": [
    { "name": "信息经济学", "title": "私人信息改变市场的均衡与效率",
      "scope": "讲私人信息的主题：逆向选择、信号、甄别、委托—代理。",
      "groups": [ { "name": "市场", "items": [ { "tree": "130", "reason": "逆向选择让市场萎缩。" } ] } ] }
  ],
  "register": [
    { "term": "逆向选择", "refs": ["tree:130", "field:信息经济学"] }
  ]
}
```

`tree` 写主题号。`refs` 里 `tree:<号>` 指那个主题，`field:<名字>` 指那个领域。任务文件列出现有领域时，保留它们的 `name`。

## 步骤（主题任务每个主题最多 5 条命令，领域任务最多 4 条命令）

1. 读任务文件里该主题的卡片清单。需要时用 `HELPER` 读一两张卡（`get_card`、`get_tree` 或 `search_cards`，只读）。读卡最多 2 条命令。
2. 想清楚分组，再用写文件工具写 JSON 文件。只写任务文件给出的文件。
3. 按下面的“自查”检查这个文件。自查最多 3 条命令。

## 自查

任务文件为每个输出文件给出一行 `SELF-CHECK:` 命令。这个命令用脚本和 ZT 以后用的规则检查你的文件。它不写卡片。

1. 写完一个 JSON 文件后，运行这个文件的 `SELF-CHECK` 命令。
2. 命令每行报告一个问题：枢纽、问题代码、说明。最后一行是 `faults: N`。
3. 改正每一行报告的问题。再运行一次这个命令。
4. 最后一行是 `faults: 0` 时，这个文件完成。然后写下一个文件，或回复。
5. 每个文件最多运行 3 次。3 次后还有问题时，照样回复。在回复的 `errors` 里写出剩下的问题。

问题代码：

- `json`、`shape`：文件不是合法 JSON，或缺少字段。
- `tree`：主题号不对。
- `broken`：`ref` 或 `anchor` 解析不出来。脚本会丢掉这一行。
- `bare`：理由太短（公式和链接不算），或理由重复了卡的标题。
- `oversize`、`flat`：组数或行数太多，或很多行只分了一组。
- `unlisted`：漏了模型卡、线索枢纽或必须写的线索枢纽。
- `anchor-title`：枢纽标题和它所挂的卡标题相同（只差空格或大小写也算）。改写成说明入口作用的标题。
- `mirror`：主题枢纽只按地址顺序抄了本树的卡，没有树外的卡。不要写它：在 `topic` 里写 `entries`。
- `entry`：`entries` 用不了：这棵树已经有主题枢纽，或有必须写的线索枢纽，或某一项不是本树的实质卡。按说明改写。
- `isolated`：主题枢纽没有列出本树以外的卡。
- `upward`：枢纽列了同级或更高一级的枢纽。
- `kind`：关系词不在清单里。
- `size`：领域的主题数不在 `field_min` 到 `field_max` 之间。
- `R2`、`R3`、`R4`、`R5`、`R7`、`R9`：理由或组名违反卡片语言（句子太长、分号、被动、“进行”类动词、“的”太多、对冲词或夸赞词）。

## 修正

脚本建卡后，ZT 会检查每张枢纽。有问题时你会收到“修正”消息，列出枢纽地址和问题，例如 `bare`（理由太短）、`oversize`（行数或组数太多）、`isolated`（没有走出本树）、`mirror`（只按地址顺序抄了本树）、`unlisted`（漏了模型卡或线索枢纽）、`entries`（主题卡的“## 入口”一节不见了或不再有效）。只改 JSON 文件里有问题的部分。改完后按“自查”运行消息里的 `SELF-CHECK` 命令。

## 回复

全部文件写完后，只回复一行 JSON，不加其他文字：

- 主题任务：`{"job":"t01","files":["…\\hub-130.json"],"topics":3,"lines":2,"errors":"无"}`
- 领域任务：`{"job":"f01","fields":6,"terms":52,"errors":"无"}`

## 通用写入规则（每个写卡的任务都适用）

- **保留术语写法。** 正文里已有的术语链接 `[[词@地址]]` 原样保留；要提到一个已有术语、而正文没有现成链接时，写术语本身的文字，不要自己造链接。
- **不编造、不绕过。** 不要编造地址或链接目标，也不要为了让检查通过而换同义词、换关系词或改掉事实里的用词。
- **先自查。** 任务文件给出自查命令时（`SELF-CHECK:` 行，或 `CHECK:` 与 `LIMITS:` 两行），原样照抄，写完（或改完）就运行；最后一行是 `faults: 0` 才算通过，最多运行三次。命令没有打印 `faults:` 行（或任务文件指定的状态行）时，视为没有自查。
- **`card_check` 是内容问题。** 写入被拒绝为 `card_check` 时，拒绝里的每个故障行就是要改的内容：按它们改写后再写一次，仍在这一轮限定的修正次数以内。它不是脚本、服务或网络故障，不要原样重试。
- **`card_locked` 是选址决定。** 写入被拒绝为 `card_locked` 时不要重试，不要换 Access，不要改用别的写入路径或直接改数据库：保留已写好的答案，按任务文件的要求回复，并写明被拒绝的地址。
