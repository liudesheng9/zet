# 讲清推导分卡：任务说明（所有任务共用）

你为已经写好的推导分卡补上解释。这些分卡的 **起点**、**步骤** 和 **结果** 已经复核过，是对的。读者能核对每一行，但不知道为什么这样推、结果说明什么。你写三种解释：**思路**、步骤下的 **说明** 和 **解读**。你不改卡片：你把解释写进一个 JSON 结果文件，脚本把它们插进卡片，并检查起点、步骤和结果一字不变。

本说明之后依次附上：模型的设定（符号表和术语表），然后是你的任务文件。任务文件给出结果文件的路径、上下文包的路径、模型卡的正文、这串推导分卡的正文，以及链之前的分卡（推导从它出发）和链之后的分卡（它用推导的结果）。

## 解释设计

批量构建时，任务文件在模型卡正文之后还附有“解释设计”：Sonnet 建筑师为本链写下的全链路线，以及每张分卡的“展示什么”“哪些步骤需要说明”“结果怎么解读”。

- 照设计写。思路写出设计的路线和本卡的展示；说明只写在设计点名、或你自己看出读者不能一眼看出的步骤上；解读写出设计给的意义和检验，再写下一张分卡用它做什么。
- 设计定内容，你定措辞。设计漏掉的说明可以补一条；不要改推导本身，也不要改起点、步骤和结果。
- 旧书补讲解（没有设计的任务）只按本说明和分卡正文写。

## 三种解释

- **思路**（`idea`，一到五句）：本卡证明什么；推导走哪条路，关键的一步是什么，为什么这条路走得通。在一串推导分卡中，第一张的思路写出全链的路线：依次经过哪些中间结论。不要写本卡在链中的位置（“第 2 张，共 3 张”）：脚本会加上这一行。
- **说明**（`notes`，按步骤编号，每条一到两句）：解释读者不能一眼看出的一步。分情形（写出分情形的条件）、近似或放缩（写出为什么够用）、引入新变量或新定义、取极限（写出哪一项起主导作用）、用到模型外的事实，这些步骤必须有说明。机械的一步（两边加同一项）不写说明。
- **解读**（`meaning`，一到六句）：结果对模型意味着什么；参数变化时结果怎样变；至少一个检验（特殊情形、符号或极限）；下一张分卡用这个结果做什么。

三种解释合计最多 16 句、600 字（公式和链接不计）。超出时删减，不拆分卡片。

## 解释的来源

1. 书自己的解释。上下文包列出来源小节的文件和行号。需要时用一到两条命令读原文行：`Get-Content -LiteralPath <文件> | Select-Object -Skip <起始行-1> -First <行数>`。只读与这些分卡有关的段落，不要通读全书。
2. 书中没有解释时，你自己写。每段你自己写的解释，末尾标 `（补：书中未写）`。
3. 不写结果推不出的经济含义。检验必须由结果算出（代入特殊值、看符号），不能是新的事实。原书说“可能”，解释也说“可能”。

## 卡片语言

遵守 `asd-ste100-zh` 技能和推导分卡的规则：一句只说一件事，描述句最多 40 字（公式和链接不计），不用分号，主动语态，动作用动词，一个术语一个意思（用设定的术语表），一个名词短语最多两个“的”，不堆叠限定，不用褒扬词。符号只用设定的符号表和分卡里已有的符号。新符号先用一句话定义。

## 结果文件

用写文件工具把一个 JSON 数组写到任务文件给出的结果文件路径（只写这一个文件），每张推导分卡一项：

```json
[
  {"address": "Key/11|b|a|4",
   "idea": "E 只在还款后所得超过 $w$ 时参与。先求 E 还款后剩下的现金 $R$。$\\min[c,P]$ 在 $c=P$ 处转折，所以分两种情形。（补：书中未写）",
   "notes": {"3": "不清算时，现金够还款，E 留下差额。", "4": "清算时，现金全部用来还款，E 不留现金。"},
   "meaning": "$w$ 在两边相消，所以 E 的财富不影响参与。检验：$f=1$ 时 (5.10) 化为 $y_1+y_2>K$。（补：书中未写）"}
]
```

- `notes` 的键是步骤编号（字符串）。没有说明的步骤不写键。
- 文本里不要写 `**思路**` 这类节标题，也不要写 `说明：` 前缀：脚本会加。
- 反斜杠在 JSON 里写成 `\\`。
- 一张分卡无法解释时（例如步骤本身看不懂），这一项写 `{"address": "…", "blocked": "原因"}`。分卡原有的问题（步骤超过 6 个、原有的长句）不是 `blocked` 的理由：自查把它们列为“kept”，脚本照常写入你的解释。

## 自查

写完结果文件后，运行任务文件里的 `SELF-CHECK` 命令。它用写入时的同一套检查处理你的文件，不写任何卡片：

- 每张有问题的分卡一行：地址、`explain`、问题（规则号和句子）。按这一行改正。
- `(kept: …)` 行是分卡原有的问题，不是你的，不计数，不要为它改解释，也不要因此回复 `blocked`。
- `地址 ok` 行表示这张分卡会照原样写入。
- 最后一行是 `faults: N`。

改到 `faults: 0` 为止，再回复。最多运行三次。三次后仍有问题，照常回复，并在回复的 JSON 里加 `"faults": N`。

## 补充任务

脚本检查后可能把一些分卡退回给你（同一对话里的后续消息）。它给出每张分卡的问题、新的结果文件路径和 `SELF-CHECK` 命令。只为这些分卡写新的结果文件，改正问题，再自查到 `faults: 0`。

## 回复

自查通过后，只回复一行 JSON：`{"done":3,"blocked":0}`。

## 通用写入规则（每个写卡的任务都适用）

- **保留术语写法。** 正文里已有的术语链接 `[[词@地址]]` 原样保留；要提到一个已有术语、而正文没有现成链接时，写术语本身的文字，不要自己造链接。
- **不编造、不绕过。** 不要编造地址或链接目标，也不要为了让检查通过而换同义词、换关系词或改掉事实里的用词。
- **先自查。** 任务文件给出自查命令时（`SELF-CHECK:` 行，或 `CHECK:` 与 `LIMITS:` 两行），原样照抄，写完（或改完）就运行；最后一行是 `faults: 0` 才算通过，最多运行三次。命令没有打印 `faults:` 行（或任务文件指定的状态行）时，视为没有自查。
- **`card_check` 是内容问题。** 写入被拒绝为 `card_check` 时，拒绝里的每个故障行就是要改的内容：按它们改写后再写一次，仍在这一轮限定的修正次数以内。它不是脚本、服务或网络故障，不要原样重试。
- **`card_locked` 是选址决定。** 写入被拒绝为 `card_locked` 时不要重试，不要换 Access，不要改用别的写入路径或直接改数据库：保留已写好的答案，按任务文件的要求回复，并写明被拒绝的地址。
