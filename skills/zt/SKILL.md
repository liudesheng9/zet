# ZT slip-box

ZT stores addressable Markdown **Cards** in one local archive split into two **Workspaces**:

- `human`: the user's own Cards. **Read-only for you.**
- `agent`: your Cards. You may read and change them.

Each Workspace has two **Zones**: Topic trees (rooted at a Topic such as `3/0`) and Literature trees (rooted at a Literature Card named by its BibTeX Citation key, such as `Smith2024`). Addresses are unique across both Workspaces: `3/1` is the direct successor of Topic `3/0`, `3/2` follows `3/1`, `3/1|a` branches sideways from `3/1`, and `Smith2024/1` is a note in a Literature tree. Links are written `[[address]]` in a Card body and may cross Workspaces; Cards never move between Workspaces.

## Use the MCP server

The server is registered globally as `zt` (Claude Code tools `mcp__zt__*`, Codex tools on server `zt`). Start every task by reading before writing:

1. `list_workspaces`: what exists, and your access.
2. `list_trees` (filter by `workspace`, `zone`), then `get_tree` or `get_card`.
3. `search_cards` before creating anything, so you extend or link existing Cards instead of duplicating them. `list_links` with `cross_workspace_only` shows how your Cards connect to the user's.

Writing (agent Workspace only):

- New idea area: `create_topic` with a one-line `title` and a short `body`.
- New paper or book: `create_literature` with exactly one BibTeX entry that has a `title`; its entry key becomes the Citation key.
- Grow a tree: `create_successor` with `at`, `title`, `body`, and `kind` `direct` (continue the line) or `side` (a tangent; not from a tree root).
- Change a Card: `edit_card` with `title` and/or `body` (or the whole `text`). A Literature Card's title comes from its BibTeX; change that with `edit_literature_metadata`.
- Card types: a Regular Card is an Idea Card by default; pass `type` `event` (one real-world event: what, when, where, who, source), `finding` (one empirical result from a source: 测量, 数据, 方法, 结果, 局限, 来源; one result per Card), `model` (one whole model), or `hub` (a way into one subject, with a `level`: `line`, `topic`, `field`, or `register`; see the zettelkasten skill) to `create_successor`, `insert_card`, or `edit_card` (`type` may be given alone). `get_hub` reads a Hub Card's lines, upper and lower hubs, and faults; `list_hubs` gives a Workspace's hub graph and the hubs it still needs; `get_card` lists the `hubs` that list a Card. Topic and Literature Cards are always `idea`. `get_card`, `get_tree`, and `search_cards` report `type`; `search_cards` with `type` and an empty `query` lists every Card of that type.
- Model structure: a model is its Model Card (its entry point: the question and what the model shows) plus **Model parts**, Model Cards with a `facet`. A part belongs to the Model Card it is filed under (as its successor or a successor of another part), if any, and to every Model Card that links it, so a part may be filed anywhere and serve several models; only the Model Card's Link takes a part in, not the part's Link to a Model Card. The facet is a short label you choose for what the part presents in this model (at most 32 characters, e.g. `设定`, `均衡`, `数值例子`; no list or order), and a part may carry an `emphasis`: `core` (what a reader must see) or `aside` (skippable detail). Pass `facet` and `emphasis` to `create_successor` (a facet implies `type: model`) or to `edit_card` (alone; `""` clears either). Parts relate by Links, not by order, and each Link's kind is read from the word right before it in its sentence: `依赖`/`rests on` (rests-on), `例示`/`for example` (illustrates), `对照`/`unlike` (contrasts), `放宽`/`推广` (relaxes), `对应`/`类比` (corresponds), `反驳`/`批评` (objects), none (refers); only rests-on stacks parts on the board. `get_model` with any Card of the model returns `models` (every model the Card belongs to), the Model Card, its parts (in the order the Model Card names them, then filing order) with bodies, `filed` and `also`, its `relations` (with `kind` and sentence), its `loose` parts, its `neighbours` outside the model (either way, with kind), and `issues` (a part in no model). ZT refuses to retype a Model Card that still has parts, filed or linked.
- Put a Card between two Cards: `insert_card` with `before` (an existing Regular Card) and the fields of `create_successor` gives the new Card that Card's place; that Card and its subtree move down one place and it becomes the new Card's Direct successor (`X/2` -> new, old `X/2` -> `X/3`; before `P|a`, the old `P|a` becomes `P|a|1`). `move_card` takes `to` (a free slot) or `before` (another Card's place, which moves down), and `alone: true` moves only the Card while its Direct successors move up to close the gap (refused when the Card has Side successors). Write every address as it is today; each returns a plan first (`insert` or `move` to confirm), applies it in one step, rewrites every Link, and returns the `moved` map. Re-read addresses after it.
- Elaboration level: a Model Card (no facet) carries its model's `level`: `concept` (level 1, a concept model: stated in words, the Model Card plus at most four parts, no Derivation parts) or `formal` (level 2, a formal model: built self-sufficient with Derivation parts). Pass `level` to `create_successor` (with `type: model`) or `edit_card` (alone; `""` clears it; `1` and `2` also work). A part has no level; a Model Card that becomes a part or changes type loses it. `get_card`, `get_tree`, and `search_cards` report `level`; `get_model` reports `level`, and its `build` adds `level`, `level_number`, and `beyond_level` (each Derivation part in a concept model, with its fix). A Model Card with no level is unclassified, and its build report applies the formal rules. Session: `lv <level|none>` (a model level or a hub level).
- Math form: a Model Card (no facet) may state one mathematical unit, named by its `form`: `definition`, `axiom`, `theorem`, `proposition`, `lemma`, or `corollary` (a unit: its Model Card holds the statement with labelled hypotheses `(H1)` or clauses `(C1)`), or `theory` (a Theory Card: the way into one theory; a Link from it takes in a whole unit). Pass `form` to `create_successor` (with `type: model`) or `edit_card` (alone; `""` clears it; the Chinese names 定理, 引理, … also work). `get_card`, `get_tree`, and `search_cards` report `form`; `search_cards` with `form` and an empty `query` lists every unit of that form. A rests-on Link to a unit's Model Card is a cited premise (`build.cited`), not a closure fault; a rests-on Link into a part of another unit is a `build.reach_in` fault. `get_model` reports `form` and `math`: for a unit its labels, tiers, core parts, crux step, budget (at most three `core` parts), faults (`no_example`, `no_nonexample`, `no_intuition`, `no_plan`, `no_crux`, `too_many_crux`, `over_budget`), theories, load, `used_by`, `building_block`, and `study` (the stations of Learn mode); for a Theory Card its units in dependency order with weight and load, main results, objects, `cycle`, `forward`, `tools`, `users`, and study passes. `特例 [[…]]` reads as `specializes` (a narrower concept links a broader one). Session: `mf <form|none>`. See docs/math-cards-design.md.
- Self-sufficient models: `get_model` also returns `build`, computed from Locations and Links: `setting` (the Model Card's first Side successor), `order` (every member in build order, each with `line`: `main` for the setting and its Direct successors, `side` for a part below a main-line step with `from`, `off` for a later Side successor of the Model Card, `shared` for a part taken in from another model with `home`, placed before the first step that needs it and after the shared parts it rests on; `derivation: true` for a facet starting with `推导`), `chains` (runs of Derivation parts next to each other, each with `parts`, `length`, and the members `after` and `before` it: one long step may take any number of Derivation parts), and the faults `closure` (a rests-on Link from the model's range to a Card that is not a member, with `fix`), `forward` (a main-line part rests on a later member), `unanchored` (a main-line part with no rests-on path to the setting), plus `tolerated` (premises of shared parts that stay in their home model; not faults; one that is a Derivation part carries a `fix`: take it in too) and `self_sufficient`. To share a derivation as a building block, take in every part of its chain. A model rests on parts, not on another whole Model Card: take the part in from the Model Card's 结构 list. `代入`, `推导自`, `由此推出`, and `substitut…` also mark rests-on.
- Bodies may show a paper's figure with `![caption](artifact:<sha256>)`, taken with `scholar_archive_artifact` (see below); the GUI draws it as a figure with its caption.
- Bodies may hold TeX (`$...$`, `$$...$$`) and HTML charts in ```` ```chart ```` fences; the GUI typesets the math and runs each chart in a sandbox with the card's palette (`--zt-*` CSS variables). A click on an element with `data-zt="<address>"` opens that Card. See the `zettelkasten` skill for how to structure a model and draw its charts.
- `delete_card` lists in its plan every Link from a Card that stays to a Card that goes (`links that will break`). When the deleted Card's content now lives in another Card (you merged two Model parts), pass `into` with that Card: each of those Links is re-pointed to it, so none breaks.
- `delete_card`, `move_card`, `insert_card`, and Citation key renames return a plan first and change nothing. Show the plan to the user when the change is significant, then call again with the `confirm` text the plan names (`delete`, the tree root's address, `move`, or `insert`).

Card bodies are Markdown. Compose, place, and link every Card by the `zettelkasten` skill: one idea in your own words under a claim title, placed beside the Card it continues, with Links that state their reason, in plain sentences (its "Card language" section: one statement per sentence, no semicolons, active voice, one term per meaning). Never write a Reverse links section: ZT generates it below the `<!-- zt:reverse-links -->` marker.

## Read the Scholar Archive

The `scholar_archive_*` tools read the user's local Scholar Archive (scholars, Works, abstracts, DOIs, journals, workspaces, and the PDF/Markdown documents linked to Works) through its read-only bridge. They pair and start the archive by themselves and do not need `zt up`.

- `scholar_archive_status`: the archive's identity, counts, and its read tools with their schemas.
- `scholar_archive_read` with `tool` and `arguments`: `list_scholars`, `list_works` (`query`, `scholar_id`, `journal_key`, `workspace_id`), `get_work`, `list_work_files`, `semantic_search` (`query`, `scope`), and the other read tools.
- `scholar_archive_sql`: one SELECT or schema pragma, for counts and joins.
- `scholar_archive_file` with `file_id`: Markdown comes back as `text`; for a PDF, read the returned `path`. Its `link` is the Document link `[name](scholar:<file_id>)`: paste it (with your own label) where a Card should let its reader open the source document itself; add `#page=12` to open a PDF at a page. The GUI opens a PDF in the browser's viewer and a Markdown document as a reading page with its figures.
- `scholar_archive_export`: JSON, CSV, or BibTeX of the archive or one scholar.
- Figures: `scholar_archive_read` with `list_work_artifacts` (`work_id`, or one Markdown's `file_id`) lists a Work's artifacts, the figure and table images its Markdown shows, in reading order, each with `number`, `caption`, `file_id`, `path`, and `shown` (used by the Markdown the Work shows first; prefer those). `scholar_archive_artifact` with that `file_id` and `path` (and optionally your own `caption`) keeps the image in ZET's archive and returns the `markdown` to paste into a Card, `![caption](artifact:<sha256>)`, and a local `path` you can open to look at the figure first. ZET refuses a Card that shows an `artifact:` it does not hold, so always take the figure before writing it.

Nothing here changes the archive. Copy titles, authors, and abstracts verbatim; when you file a paper in ZET, make a Literature Card from its actual metadata (DOI included) in the agent Workspace.

## Rules

- Never change the human Workspace by any route. If the server refuses a change (for example ``the human workspace is read-only for AI agents``, or a change that would rewrite Links inside a human Card), that is the user's policy, not a bug: do not work around it with the `zt` shell commands, the GUI API, or the SQLite database. Tell the user what you wanted to change and let them do it.
- Write only through the MCP server. Do not edit the archive's `zt.sqlite3` directly.
- Cite Cards by address (`3/1|a`, `Smith2024`) when you report back.

## When the server is unavailable

- A tool error saying the service is not available: run `zt status`; if it is down, run `zt up`, then retry.
- No `zt` tools at all (DeepSeek Harness has none; elsewhere the server may not be loaded): call the same tools, with the same agent Access, through the zt helper `zt-digest call` (one fast binary beside `zt`; this skill's `scripts/zt-mcp.ps1` forwards to it and takes the same arguments). Write the calls to a UTF-8 JSON file, `[{"tool": "create_successor", "arguments": {...}}, ...]`, and run `zt-digest call calls.json`, or pipe them in: `@'...'@ | zt-digest call -`; a single call can also go inline as `zt-digest call -Tool get_card -Json '{"at":"3/1"}'`. In any string argument, `@@N` becomes the address returned by call N, so one file can build a chain of Cards and link them. The output is one line per call (`N ok <address>`, `N <json>`, or `N error <reason>`), and the run stops at the first error, so re-run only from the failed call. Batch reads in one file and writes in another to save turns. The `zt` shell commands act with human Access, so never write with them.

## Developing zt itself

The source is the `zet` repository (github.com/liudesheng9/zet; a Rust crate that builds the `zt` binary). Read its `CONTEXT.md` for the domain language and `AGENTS.md` for repository workflow before changing it.

- Test with `cargo test` from PowerShell. Under Git Bash the dump tests fail because of PATH, not the code.
- Deploy a change: `zt down`, back up `<archive_root>\zt.sqlite3` when the schema changes (`zt status` prints the archive root), `cargo install --path . --locked`, `zt up`, then confirm with `zt version` and `zt status`. `zt down` refuses while a Session is open; the GUI runs inside the service and stops with it (`zt gui` prints its URL). `cargo install` also installs `zt-boot`, the login command `zt autostart on` registers; `zt autostart` shows whether it is on and how the last login start went.
- After changing a skill (`skills/zt/`, `skills/zettelkasten/`) or the server registration, re-run `scripts/install-agent-integrations.ps1` so Claude Code, Codex, and DeepSeek Harness get the update. New conversations pick up MCP changes; open ones keep the server they started with.
