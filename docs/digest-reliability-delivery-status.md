## #65: derived Link index

Implemented in `src/link_index.rs` and the existing write paths. Authored bodies remain authoritative. Ordinary edits validate referenced targets, replace one source's occurrence rows and refresh its old/new targets. Structural changes retain a full rebuild within their existing transaction. The index preserves repeated occurrences, relation kinds, Broken links and existing ordering. Metadata/text edits commit atomically with one revision; unchanged saves do not advance it.

Migration runs even for existing Markdown archives, makes an integrity-checked SQLite backup and installs its marker/index transactionally. A malformed Card names its address and rolls back. `zt status --check-links` compares the index and generated text with the full parser; `zt reindex` repairs derived data explicitly. Lock sharing violations are classified as busy and retried without removing a live holder's lock.

## #77: checked aggregate publication revisions

Aggregate publication layers (`cards-book`, `link-check`, `organize`, `skeleton`, `figures`, `bridge`, `audit`, `hubs`) no longer sit at revision 1 forever. `register` takes an explicit revision, and `ledger publish` derives the next one from a **sorted input manifest**: every contributing producer that is `done` with one order-independent fingerprint of its registered `outputs`, every other relevant producer with a stable `pending`/`unresolved` disposition and fault code, plus the preparation hash, the declared scope and the publication contract version. Scheduling states are one `pending` disposition, so a `registered`→`ready` transition alone never creates a revision while a real status change always does. Every publication also reads the Model candidates its groups registered, so a repaired or newly built model changes the input set of every downstream revision, and `organize` additionally reads the registered note suggestions it must dispose. The same manifest reuses its revision and writes nothing at all; a changed manifest registers the next revision and turns every older open revision of that key into terminal `failed`/`superseded` history naming its replacement. Done revisions are never reopened.

`ledger status -Out <out> [-Layer <layer>]` now returns a `publications` array selecting the latest revision of every logical key, whether it still describes the present inputs (`current`), and exactly which earlier revisions it superseded. Superseded revisions are excluded from `failed`, from `unresolved` and from `ledger rerun-list`, and `ledger next` can never hand one out. Registering a revision seals that layer's enumeration barrier, so a revision becomes claimable exactly when its producers settle; an aggregate layer whose required publication is missing is not `settled`, which keeps a deleted publication visible instead of reading as an empty queue.

A publication is completed by `ledger done -Unit <layer>/<key>@<revision> -Outputs <out>/publication-<layer>-<key>-<revision>.json`. The evidence must account for the entire manifest it was registered with — `consumed` entries must match the recorded contribution fingerprints exactly, `unresolved` entries must be manifest dispositions, the two must be disjoint and together cover every entry — and its `disposition` follows from that accounting (`no_work`, `published`, or an honest `partial`). It must also name exactly the layer's compiler artifacts (`decisions`/`applied`, `skeleton`, or `report`), which the ledger canonicalizes and hash-binds. Layer coverage sets are checked: `organize` must dispose every registered note suggestion with that suggestion's own retained outcome; a skeleton must classify every prepared anchor as indexed substantive work or a named gap; figures must account for every prepared reference with unchanged path/hash when shown; a Bridge report must recompute its own `r-<Content-Hash>` id and account for exactly its proposal set with open proposals recorded as review decisions.

Each independent note suggestion is its own `notes/<id>@1` unit, registered against the Card state it was made from, and completes with exactly one archive-checked outcome: `applied` (the proposed Link is authored and the Card changed), `already_present` (authored and unchanged) or `refused` with a source or relationship reason. A hub refresh is coalesced by touched tree and must declare that tree with its required upper hubs and Register before it registers; the declared scope is part of the manifest, so changing it derives a new revision. `ledger relocate -Moves <file>` applies a recorded structural mapping to every published Card locator — accepting the helper's own `-Moves` log — and refuses with `unreconciled_move` naming the exact addresses when a published address vanished with no recorded mapping.

## #84: bounded lock waits and daemon restart diagnostics (DG21, verified 2026-10-18)

#84 makes a long edit wait and an unexplained daemon disappearance diagnosable, and makes every digest stage recover from a restart instead of hanging or blindly starting services. Acceptance criteria and their public evidence:

- **Typed lock contention, not one busy blob (R314).** `try_acquire_edit_lock` now returns `EditLockError::Busy(EditConflict, …)` or `EditLockError::Fault(anyhow::Error)`. `EditConflict::Held` is another holder's marked file, with the pid or marker that could be read of it; `EditConflict::Sharing` is Windows `ERROR_SHARING_VIOLATION` (os error 32) or the byte-range `ERROR_LOCK_VIOLATION` (os error 33) that a live holder's `LockFileEx` produces while the lock is opened, read or removed. Access denied, a full disk, a lock file that is not UTF-8 text and every other IO error are faults that fail at once and keep the file for its owner. The two contention codes are only read as contention on Windows; on other platforms those numbers mean unrelated errors. `tests/workspaces_mcp.rs` proves it at the command boundary: `a_lock_fault_is_reported_instead_of_being_waited_out_as_if_it_were_busy` (a directory where `zt.edit.guard` belongs fails in under ten seconds, names the file and is not `edit in progress`) and `a_malformed_lock_file_is_a_fault_that_keeps_the_file_for_its_owner` (invalid bytes keep the file byte-identical and create no Card). The existing live-holder and sharing-violation tests still pass unchanged.
- **Finite patience in seconds, propagated to the actual child (R315).** `zt mcp` validates `ZT_EDIT_PATIENCE` as whole seconds from 1 through 300 (default 20) and writes one `edit patience: ZT_EDIT_PATIENCE=<value> is not a whole number of seconds from 1 through 300; using the default 20` line for a declared value it refuses, so a batch client's misconfiguration cannot silently fall back (`an_invalid_edit_patience_is_reported_once_and_the_documented_default_applies`). `apply_batch` now takes the client's declared patience instead of a hardcoded 20 seconds, so the digest's batch writes honour its 180. `service-health.tests.ps1` holds the real lock file without delete sharing and runs a real `zt-digest call` write with no patience in its own environment: the child's line carries `patience_s=180` and the write commits after the holder releases.
- **One wait event, one completion, both durations (R316/R317).** A wait longer than five seconds writes exactly one `edit wait: op=… waiter_pid=… elapsed_ms=… patience_s=… holder=…` line; its release writes exactly one `edit wait done: op=… outcome=acquired queue_wait_ms=… held_ms=…` line, and a wait that overruns its patience writes exactly one `outcome=timeout` line with `waited_ms` and `patience_s`. A hold longer than five seconds with no wait writes one `edit lock held:` line with both durations. The poll loop never writes a line per poll, and a live holder's lock file is never removed for it (`a_contended_batch_write_logs_one_wait_event_and_one_completion_with_both_durations`, `a_wait_that_overruns_the_declared_patience_logs_one_timeout_and_keeps_the_live_holder`, and the same two cases in `service-health.tests.ps1`). The shell and Session paths name their operation (`"session n"`, `"move"`, …) but keep refusing at once; small transactions and batching remain the fast path.
- **Daemon records, panic hook and heartbeat (R318/R319).** The daemon writes `zt.daemon.run` (pid, version, archive id, revision, start time, last heartbeat, panic mark) and logs `daemon started pid=… version=… archive=… revision=…`; every normal exit path (`zt down`, sign-out, shutdown) logs `daemon stopped … exit=normal reason=… uptime_s=…` and removes the record. A panic hook logs `daemon panic: … message=… location=…` and marks the record. The next start that finds a record logs `daemon abnormal exit: pid=… version=… archive=… revision=… started=… last_heartbeat=… panicked=… exit_info=none cause=unknown` and keeps it as `zt.daemon.last`, which `zt status` reports as `last_exit: abnormal` until a normal exit clears it. A minute heartbeat appends `daemon heartbeat pid=… version=… archive=… revision=… run=… unit=… marker_age_s=…` while ledger-aware digest commands keep `<archive>/zt.digest.run` fresh (written by `zt::renew_active_run` at every digest client start and by each claimed unit's heartbeat, 300-second lifetime), and stops when the renewals stop. The tests are `a_normal_stop_records_pid_version_archive_and_revision_and_leaves_no_abnormal_record`, `a_force_killed_daemon_is_reported_as_an_unknown_abnormal_exit_at_the_next_start`, `a_panicking_daemon_records_the_panic_and_the_next_start_reports_it` and `a_heartbeat_names_the_active_digest_run_and_stops_when_its_marker_expires` in `tests/autostart.rs` (the panic and the short heartbeat interval exist only for an isolated `ZT_CONFIG_DIR` under the temp folder). No exact cause is claimed for a force kill or a power cut: the record says `exit_info=none cause=unknown`, and `service-health.tests.ps1` asserts that wording at the command boundary.
- **Stage health checks that wait without duplicating daemons (R320/R321).** Every `zt-digest` command that opens the archive client resolves the service first (`zt::start` → `zt_check::mcp::ensure_service`): it queries `zt status`, parses `state:`, `pid:`, `archive_root:`, `revision:` and `last_exit:`, and polls at 500 ms intervals for at most 120 seconds. It never launches a daemon: `zt status` is the one path that clears a stale record and starts one service, so concurrent stages share one restart. A service that stays down is one typed `infrastructure_fault` that names the wait and leaves the run's units and files untouched. A valid restart means the next command starts a fresh child client; the identified helper's receipt replay is what reconciles writes a disappearance interrupted. `zt-digest service-wait [-Wait 0..120] [-Out <folder>]` is the explicit stage/operator form and reports `{ok, state, waited_ms, pid, archive_root, archive_revision, last_exit_abnormal, reconnected, stage}`. `service-health.tests.ps1` covers it end to end: a force-killed daemon (T27) leaves its record; the next stage command records exactly one restart and one abnormal exit naming the dead pid, reports `reconnected: true` and the same archive revision, the same receipt-identified write replays to its original address with no new revision, exactly two `daemon started` lines exist in the whole log, and a service stopped with `zt down` yields exit 4 with `code: infrastructure_fault` and no daemon launched. Because every stage command is a `zt-digest` tool, every stage and every retry passes through this resolution; `framework-harness.mjs` asserts that no stage bypasses the tool (`service: every stage command is a zt-digest tool …`, R320), so the workflow needs no separate health command and no new watchdog service exists.

## #86: the finite finalization branch (DG23, verified 2026-10-18)

Finalization is the declared finite sequence `audit-plan → at most one compiler correction cycle → refresh affected downstream publications → final read-only audit`, and it is now one command boundary (`zt-digest finalize`) plus one workflow stage (`zt-finalize`): no undeclared loop exists to re-enter it.

- **The audit plan (R299, AC1/AC5).** `finalize -Step plan` publishes the scheduling audit revision when it is still open (the audit stage's report becomes that revision's checked `report` artifact) and derives one immutable `<out>/finalize/audit-plan.json` from `audit-faults.txt` and `audit-cards.json`. Every fault gets one disposition: `fix` (a writable Card — idea, event, finding, anchor — whose audited authored projection still matches the current archive), `conflict` (the Card changed after the audit it scheduled, so a rewrite from that stale base is refused), `blocked` (a Model, Model part, Hub, structure or term-table Card: correcting it would reopen a done build), `stale` (the audited Card no longer exists), or `advisory` (I1, I6, E5, L3 and `N1`). The branch is therefore `no_fix` (nothing hard to correct), `fix` (at least one correctable Card), `conflict` (only stale bases remain) or `unresolved` (only faults the bounded branch may not rewrite). One correction cycle is declared — `fix_cycle {permitted: 1, used: 0, rules, cards, card_list}` — and the plan writes the exact Card list to `finalize/fix-cards.txt`. A recorded cycle (`fix-cycle.json`) makes the plan immutable: a second plan or scope is refused, so the branch cannot loop.
- **The one correction cycle (R299, AC1/AC3).** The Card compiler gains `-Cards <file>`: the cycle picks exactly the plan's Cards (a Card outside it is never picked, so the cycle cannot widen into the book) and checks exactly the plan's `-Rules`. `zt-digest-lib` v11 adds the declared `fixRounds` bound, so the finalization spends one round whatever the run's `cardFixRounds` pilot setting says. Whole-book content generation, the digest groups and every done Model build stay untouched.
- **The changed-Card manifest (AC2).** `finalize -Step scope` records once what the cycle changed: per Card its kinds (`structure`, `links`, `figures`, `new`), category, tree and the before/after authored projection, plus the touched trees and a `change_hash`. It compares the audited projection the audit retained (title, body, facet, Links, figure references) with the current archive, so a projection difference is never mistaken for a real edit. `finalize -Step refresh -Layer <layer>` then publishes one affected aggregate publication at a new revision whose declared `scope` is that manifest — through the same verified `publication_finish` boundary (`consumed`, `unresolved`, `disposition`, exact hash-bound artifacts, coverage) — and the identical manifest reuses the registered revision instead of deriving another. The plan names, for every layer, whether this branch re-derives it (the Link check from the cycle's own report, and the final audit) or whether its own stage owns that content (Organize's Opus decisions, the skeleton job, the Hubs plan, the Bridge judges, the mathematics theory summary); a stage-owned layer is reported with that reason and is never republished from an artifact this branch did not re-derive. The changed-Card manifest remains that stage's recorded input.
- **The final read-only audit (R300, AC4).** `finalize -Step final` runs the read-only audit again into `finalize/final-audit` (or verifies a given report) and refuses a report at or before the scheduling revision, so the final audit is always after the corrections and refreshes. It publishes the next `audit/book@N` revision with the change scope and writes `finalize/final-report.json` and `final-report.md`: the new `graph_revision`, the scheduling and final audit revisions kept distinct, the change facts, every refresh fact (unit, revision, state, refreshed/stage-owned), every residual fault by class (`hard`, `source`, `infrastructure`) and the status — `done` only when no hard/source/infrastructure fault remains, otherwise `partial`. The superseded scheduling audit keeps its checked completion as history.
- **Workflow wiring (AC5).** Base 3.3.0 adds the `finalize` stage after `audit` and before the settlement (`args.finalize`, default true, skips it), so the graph is `… → bridge → audit → finalize → cleanup → report`; the mathematics `math-check` now follows `finalize` and therefore describes the final audit revision. `zt-finalize` v1 runs plan → (one scoped cycle) → scope → refresh → final and returns `{status, branch, plan, cycle, scope, refreshed, final}`; `zt-digest-report` v9 carries `finalize` in every full result.
