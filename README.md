# ZT

English | [中文](README.zh-CN.md)

ZT is a local note system built around addressable Markdown Cards, with a terminal Session and a slip-box GUI.

## Features

- Write every Card in Markdown: a `# Title` heading, a Markdown body, and generated Reverse links.
- Browse and edit in `zt gui`: a card cabinet, a Folgezettel map laid out by address, a Constellation of all Cards, and a live Markdown writing desk.
- Organize notes as Topic trees and Literature trees: each Topic and each BibTeX-backed Literature Card is the root of its own tree of Regular Cards.
- Mark a Regular Card as an Event Card (one real-world event) or a Model Card (one whole model); the other Cards that cite it link to it.
- Keep two Workspaces, one for you and one for an AI agent, each with a Topic zone and a Literature zone; Links cross between them, Cards never move between them.
- Let coding agents work in the agent Workspace through the `zt mcp` server, with read-only access to yours.
- Navigate Cards by Location or Citation key in an interactive terminal Session.
- Connect Cards with `[[target]]` Links, with generated Reverse links and Broken link checks.
- Safely create, edit, move, and delete Card trees from the Session or shell.
- Store everything locally in SQLite, with status, statistics, dump, and clear commands.

## Install

Install the Rust toolchain, clone this repository, and run:

```sh
cargo install --path . --locked
```

## Quick start

Choose a directory for ZT's local data, start the service, and open a Session:

```sh
zt config set archive_root "<data-directory>"
zt up
zt
```

Inside the Session, commands are entered without the `zt` prefix:

```text
t My first topic   # Create a Topic
n                  # Create the Direct successor (also works on a Literature Card)
b                  # Create a Side successor
l                  # Create a Literature Card
e                  # Edit the current Card
ty event           # Make the current Card an Event Card (or ty model, ty idea)
ws [agent|human]   # List Workspaces, or switch to one
go <target>        # Go to a Location or Citation key
up                 # Go to the parent Card (a tree root goes to ROOT)
ls                 # List the current tree, or Topics and Literature at ROOT
help               # Show the commands available here
q                  # Quit the Session
```

The ROOT view lists every Topic and Literature Card. Every Card view ends with
clickable `parent:`, `direct:`, and `side:` links. `ls`, `lsbk`, and `help` open a
panel whose addresses you can click; press `Esc` to close it. Long views scroll
with `PageUp`/`PageDown` or the mouse wheel.

## Markdown Cards

Every Card is stored as one Markdown document:

```markdown
# Atomic notes

One idea per card. See [[0/0]] and [[Smith2024]].

- short
- linkable

<!-- zt:reverse-links -->
## Reverse links

- [[0/2]] Addresses are places
```

The `# Title` heading is required for Topic and Regular Cards. Everything after the
`<!-- zt:reverse-links -->` marker is generated by ZT and rewritten on every save, so edits
there are ignored. `[[target]]` Links work in prose; inside `inline code` or fenced code
blocks they are plain text. The terminal never renders Markdown: the Session shows and edits
the stored Markdown exactly as written.

Archives created before 0.2.0 are converted automatically on `zt up`; the original database
is first copied to `zt.sqlite3.pre-markdown-<time>.bak` in the archive root.

## The GUI

With the service up, run:

```sh
zt gui                 # opens an app window (Edge/Chrome) or your browser
zt gui --no-open       # just print the local URL
zt gui --port 4717     # choose the port
```

- **Cabinet** (left): tabs for the human and agent Workspaces, the Topic and Literature zones of
  the open one, and full-text search.
- **Desk** (ROOT): each tree of the open Workspace as a stack of index cards, grouped by Zone.
- **Map**: the current tree as a Folgezettel map seen through a focus lens. Direct successors
  run down a column and Side successors branch into the next column. The Pointer card is pulled
  forward; its path, children, and neighbours stand up as cards; the rest lie as one-line slips,
  and branches away from the Pointer fold into "+N" stacks. Only the Pointer's Links are drawn.
  Press `x` to unfold the whole tree.
- **Constellation**: every tree as a radial outline set around one ring, with the Links between
  two trees bundled into one arc weighted by their count. The Pointer's tree stands out.
- **Reader** (right): the Card as a ruled index card, with its address stamp and title above the
  red line and its Markdown written on the blue rules; Link chips, Reverse links, actions, and the
  stored Markdown lie below it. The Map and arrow keys handle parent/direct/side moves.
- **Writing desk**: raw Markdown next to a live preview, `[[` Link completion,
  `Ctrl+S` to save, and `Esc` to cancel.

The command bar speaks the Session's language (`go 1/2`, `n`, `b`, `e`, `t Title`, `l`,
`ws agent`, `del`, `mv 1/3`, `ty event`, `lsbk`, `help`). Delete, move, and Citation-key rename ask you to type the
same confirmation as the CLI. Keys: `:` command bar, `/` search, `g` go, `n` `b` `e` `m`,
`Delete`, `u` or arrows to walk the map, `x` to unfold or fold the tree, `v` to switch views,
`w` to switch Workspaces, `f` to fit.

The GUI listens on `127.0.0.1` only, requires a per-launch token, and counts as a Session,
so `zt down` waits until you close it with the power button or `Ctrl+C`.

## Workspaces

One archive holds two **Workspaces**: the **human** Workspace for your own notes and the
**agent** Workspace for an AI agent's. Each Workspace has two **Zones**: a Topic zone and a
Literature zone, each holding any number of trees.

- Every tree belongs to exactly one Workspace, and new successors join their tree's Workspace.
- Addresses are unique across both Workspaces, so `[[target]]` Links (and their Reverse links)
  cross freely between them.
- Cards and trees never move between Workspaces: `mv` refuses a destination in the other one.
- Archives created before Workspaces existed are upgraded on `zt up`, with every Card in the human
  Workspace.

```sh
zt ws                          # list both Workspaces and their Zones
zt t --ws agent "Agent topic"  # create a Topic in the agent Workspace (default: human)
zt l --ws agent                # create a Literature Card in the agent Workspace
```

Inside a Session, ROOT shows the current Workspace's Zones. `ws` lists both Workspaces and
`ws agent` / `ws human` switches; `t` and `l` create in the current Workspace, and following a
Link into the other Workspace switches to it. In the GUI, the cabinet's two tabs (or `w`, or the
`ws` command) switch Workspaces, agent Cards carry a violet AI AGENT tag, and Links into the
other Workspace are inked in its color.

## Event and Model Cards

Every Card has a **Card type**. Most Cards are **Idea Cards** (`idea`, the default): one idea in
your own words. A Regular Card may instead be

- an **Event Card** (`event`): one event that happened in the real world (what, when, where,
  who, and the source that reports it), with no interpretation in its description; or
- a **Model Card** (`model`): one whole model (question, setup, assumptions, timing and
  information, solution, results, intuition, limits, source).

Idea Cards cite them with ordinary `[[target]]` Links, so a Model Card's Reverse links list every
Card that discusses the model. Topic and Literature Cards are always Idea Cards. The type stays
with the Card when it moves, when Side successors are compacted, and when a Citation key is
renamed; it changes nothing else about the Card. Archives created before 0.5.0 are upgraded on
`zt up`, with every Card an Idea Card.

- **Session**: the Card view shows `[event]` or `[model]` after the Location; `ty event`,
  `ty model`, or `ty idea` sets the type of the current Regular Card.
- **GUI**: Event and Model Cards carry an EVENT or MODEL stamp on the Reader card, in the map,
  and in search results, and each desk stack counts them; the writing desk of a Regular Card has a
  type selector, and the command bar takes `ty`.
- **MCP**: `create_successor` and `edit_card` take `type` (`idea`, `event`, or `model`;
  `edit_card` accepts it alone), `get_card`, `get_tree`, and `search_cards` report it, and
  `search_cards` filters by `type`, with an empty `query` listing every Card of that type.
- **Dump**: `archive.json` lists the non-Idea Cards under `types`.

## The MCP server

`zt mcp` runs a [Model Context Protocol](https://modelcontextprotocol.io) server over stdio, so
coding agents can work in the slip-box. It can **read both Workspaces** but **change only the
agent Workspace**: every write to the human Workspace is refused, as is any agent change that
would rewrite a Link inside a human Card (for example moving or renaming an agent Card that a
human Card links to). Agent Links into the human Workspace are fine; they only add generated
Reverse links to the human Card.

| Tool | What it does |
| --- | --- |
| `list_workspaces` | both Workspaces, their Zones, Card counts, and your access |
| `list_trees` | tree roots, filtered by Workspace and Zone |
| `get_tree`, `get_card` | one tree, or one Card with its neighbors and Links in and out |
| `search_cards`, `list_links`, `list_broken_links` | full-text search (optionally of one Card `type`), the Link graph (optionally only cross-Workspace Links), Broken links |
| `create_topic`, `create_literature` | start a Topic or Literature tree in the agent Workspace |
| `create_successor` | add a direct or side successor to an agent Card, optionally an Event or Model Card (`type`) |
| `edit_card`, `edit_literature_metadata` | change an agent Card's title, body, type, or BibTeX |
| `delete_card`, `move_card` | delete or move agent Cards |

Deletes, moves, and Citation key renames first return a plan; call again with the `confirm`
text it names (`delete`, the tree root's address, or `move`) to apply it. The service must be up.

Two agent skills come with zt: `zt` (`skills/zt/SKILL.md`) teaches the Workspaces, tools, and
rules, and `zettelkasten` (`skills/zettelkasten/SKILL.md`) teaches how to compose a Card and
connect it, after Niklas Luhmann's practice and later practitioners' experience (sources in
`skills/zettelkasten/references/`). To make the skills available in every Claude Code, Codex,
and DeepSeek Harness conversation, and the server in Claude Code and Codex, run once on Windows, and again after updating a skill
or moving the `zt` binary:

```powershell
pwsh -File scripts/install-agent-integrations.ps1
```

It copies each skill to `~/.claude/skills/<name>` and `~/.codex/skills/<name>`, links
`~/.dsh/skills/<name>` to the Codex copy for DeepSeek Harness, registers `zt` as a
user-scope MCP server in Claude Code (allowing its tools) and as a global server in Codex, and
checks the server's handshake, backing up each config file it changes. Conversations that are
already open keep their old servers. Elsewhere, `claude mcp add -s user zt -- zt mcp` or
`codex mcp add zt -- zt mcp` registers the server by hand; any other MCP client can launch
`zt mcp` as a stdio server the same way.

## Scholar Archive

ZET reads the local [Scholar Archive](https://github.com/liudesheng9/google_scholar_archive)
through the **Scholar Archive bridge**, an authenticated, read-only connection with a connector on
each side. ZET sees everything the archive holds: scholars, Works with their sources, versions,
abstracts and topics, journals, workspaces, source history, the linked PDF and Markdown documents,
any table through read-only SQL, semantic search, and whole exports. Nothing ZET does through the
bridge changes the archive, and nothing read through it changes a Card.

The connection runs by itself. The first use pairs ZET by running `scholar-archive bridge pair`
(installed with Scholar Archive) and keeps the credential in ZET's config folder as
`scholar-bridge.json`. Every request is signed with that secret, and ZET accepts only answers
signed back with it, so only the paired ZET can read the archive and ZET knows it reads the real
one. If the archive no longer knows the credential, ZET pairs again; if its server is stopped, ZET
starts it.

```text
zt scholar                         # connect and show the archive's identity and counts
zt scholar tools                   # the archive's read tools
zt scholar call list_works '{"query":"democracy","limit":5}'
zt scholar call get_work '{"work_id":42}'
zt scholar sql "SELECT id, title, year FROM works WHERE doi IS NOT NULL LIMIT 10"
zt scholar file 22                 # fetch a document, SHA-256 checked, into ZET's cache
zt scholar export --format bibtex --out works.bib
zt scholar pair --rotate           # issue a new secret; `zt scholar unpair` disconnects
```

`zt mcp` offers the same reads to agents as five read-only tools: `scholar_archive_status`,
`scholar_archive_read` (any of the archive's read tools), `scholar_archive_sql`,
`scholar_archive_file` (Markdown comes back as text, PDFs as a cached path), and
`scholar_archive_export`. They do not need the ZET service to be up. The protocol is in
[doc/scholar-archive-bridge-design.md](doc/scholar-archive-bridge-design.md).

## Dumps

`zt dp` writes a compressed archive under `<archive_root>/dump/` that records the whole card
system:

- `mapping.json`: every Card address mapped to its Markdown file.
- One Markdown file per Card holding its exact stored text; a Literature Card's file starts with
  YAML front matter holding its BibTeX, and `<citation-key>.bib` holds the exact BibTeX bytes.
- `archive.json`: the Workspace of every Card address, the next Topic number (so deleted
  Topic numbers are not reused), and the type of every Event and Model Card, for example
  `{"next_topic_id":3,"workspaces":{"0/0":"human","0/1":"human","1/0":"agent"},"types":{"0/1":"event"}}`.

`zt dp` offers each format (`zip`, `tar.gz`, `tar.zst`, `7z`) that a tool on the host can
really write: it tries every `tar`, `zip`, or `7z` on `PATH` and keeps the first whose probe
archive carries the right format signature. On Windows a GNU tar from Git for Windows is passed
over for the bundled `tar.exe`.

## Create a Literature Card

Run `l` inside a Session, or run `zt l` from the shell (using `$EDITOR`). Enter and save one complete BibTeX entry, then enter and save the Card body. The BibTeX entry key becomes the Citation key, and its `title` field becomes the Card title.

```bibtex
@book{Smith2024,
  title = {Example Book}
}
```

Inside a Session, press `Ctrl+S` to save each stage or `Esc` to cancel. You can later open this Card with `go Smith2024` or link to it with `[[Smith2024]]`.

## Literature trees

Each Literature Card is the root of its own tree for notes about that work. The
Literature Card keeps its BibTeX metadata; its tree Cards are Regular Cards:

```text
go Smith2024   # Open the Literature Card
n              # Create Smith2024/1
n              # From Smith2024/1, create Smith2024/2
b              # From Smith2024/2, create Smith2024/2|a
```

Literature tree Cards follow the same successor, link, move, and delete rules as
Topic tree Cards, with one boundary: they can move only inside their own
Literature tree, and Topic tree Cards cannot move into a Literature tree.
Renaming the Citation key through `e` → metadata renames the whole tree and
rewrites every Link to it. Deleting a Literature Card deletes its whole tree and
asks you to type its Citation key, just as deleting a Topic asks for its
Location.

## Card addresses

ZT does not use arbitrary IDs for Topic and Regular Cards. It automatically assigns each one a **Location**:

- A Topic uses `<topic-number>/0`; a fresh archive starts with `0/0`, then `1/0`, and so on. Normal deletion does not reuse Topic numbers.
- `n` creates a numbered Direct successor: `0/0` -> `0/1` -> `0/2`.
- `b` creates the next lettered Side successor of a Regular Card: `0/2|a`, `0/2|b`, ... `0/2|z`, `0/2|aa`.
- A Direct successor after a Side successor starts a new numbered segment: `0/2|a` -> `0/2|a|1`.
- A Literature Card has no Location. Its BibTeX entry key is its Citation key.
- Cards in a Literature tree use the Citation key in place of the Topic number: `Smith2024/1`, `Smith2024/1|a`.
